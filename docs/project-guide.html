01项目概览

砍价是一个到店消费的议价代理原型。它要验证的不是「AI 说话像不像人」，而是：用户不用重复查找、重复说明，几步就能拿到一个说得清、能执行的价格。

用户在 OTA、团购页或商家聊天里看到一个报价，截图上传；系统识别出门店、项目、总价和条件；用户确认或修正；助理按这些条件打电话去谈，谈完给三种明确答复之一。整个过程中，用户只需要做三次决定：传哪张图、条件对不对、要不要现在问。

到店消费代客议价截图识别异步任务 微信留资可追溯沟通记录

它现在是什么

  • 产品原型：用于讨论形态和流程，不是可商用服务。所有商家、电话、微信、价格、通话内容都是本地演示数据，页面不发任何网络请求。
  • 可演示：双击 index.html 就能跑；手机宽度下自动去掉拟真外框铺满全屏；压缩包可直接发给别人。
  • 可扩展：加一个品类只改 CATS 配置，渲染与流程代码不动。

02目标用户与场景

目标用户

已经看中某个门店或套餐、但觉得价格还能再谈的普通消费者。两类人：订酒店民宿的出行人群，和到店娱乐消费的人群（KTV、按摩足疗、酒吧、健身房、洗浴桑拿）。

共同特征：手里有一个明确报价，但不擅长、也不愿意自己开口砍价。他们不缺信息，缺的是「替我去问」的那个人，以及一个不用寒暄、不用来回拉扯的过程。

典型场景

周五想订周六的 KTV 中包，团购页写 1,480 元 4 小时。用户不确定这个价是不是最低、能不能送果盘、开台费能不能免。让他自己打门店电话，要重复说人数、时段、包型，还要面对「这个我得问一下」的等待。这个 Demo 把这一段整个接走：传图、确认、等结果。

非目标

  • 不做比价搜索引擎：只处理用户主动上传的这一张报价。
  • 不做通用客服：不回答门店营业时间、路线之类的问题。
  • 不做交易闭环：不收款、不下单、不出订单号。

03做什么，不做什么

做

  • 截图识别：门店、项目、总价、计价单位、已含权益
  • 字段可改、可删、可加；只有店名和单位必填
  • 给出议价目标区间（标价 × 0.85 起谈）
  • 代打电话、确认条件、谈直订价
  • 三种结局都给明确答复，不编价格
  • 成交后索取商家微信 / 企业微信，结果页可复制
  • 异步任务：可离开、可通知、刷新可恢复
  • 沟通记录完整保留，可逐段展开

不做

  • 不做医美等医疗合规品类
  • 不做真实支付、下单、预订
  • 演示阶段不拨真实电话
  • 不承诺「一定砍成」
  • 未接通不推测价格或优惠
  • 不出虚假订单号、支付成功状态
  • 不代用户付款
  • 非成交询价不索取、不展示联系方式
一条硬规则：截图里没有的条件，助理不会替用户猜，会在通话里当场问；问不到就写「未确认」，不用默认值填空。

04业务流程图

主链只有一条，分叉只有两个：接没接通、愿不愿意让价。角色用颜色区分——用户负责三次确认，助理负责识别与代谈，商家只在通话里出现。

三条核心规则

  1. 必填只有两项：店名和询价单位。其余字段都可改、可删、可加——截图里没有的东西，助理不猜。
  2. 只记消费总价：单位作为分母挂在后面（¥1,480 / 4 小时），不做「每晚价 / 全程总价」切换。
  3. 目标价 = 标价 × 0.85：结果页必须落在 [目标, 标价] 区间；谈不到就如实报原价，不美化。

06状态流转与数据模型

最容易误读的一点：记录的状态只有两个——running 和 done。「已取得优惠 / 商家无优惠 / 未接通」不是三个状态，而是 scn 标签，在发起询价时确定，决定结果卡文案和按钮。

三个数据结构

对象存放关键字段
state 草稿 内存，未落库 scenario, store, unit, price, list, fields[{l,v}], needs[], contact{name,phone}, shotURL
rec 记录 kanjia.records.v2 id, cat, store, unit, price, wx, fields, needs, meta, scn, status, startedAt, durationMs, notify, notifyVia, contact, time, res, finishedAt
CATS[cat] 配置 代码常量 store, unit, price, list, ratio, merchant, tel, wx, fields, missing, needsDefault, ask, ava, step2, winBenefit, winExtra, rule, noneReason, noneFree, labels

rec.res 是结算时生成的快照：{pill, pillText, head, price, old, tag, note, rowsTitle, rows[], extra, warn}。结果页只读快照，不再重算，这样历史记录不会因为改了配置而变样。

面试/评审常问：为什么不把 win / none / fail 做成三个状态？因为它们不是生命周期阶段，而是同一次结算的三种结果标签；状态机只需要关心「是否还在跑」。分开做会导致状态爆炸（running-win、running-none…）。

07关键实现

1. 进度是时间轴，不是定时器堆叠

没有用一串 setTimeout 推进 UI，而是只用一个 250ms 的 ticker，每次用 elapsed = Date.now() - startedAt 去查当前阶段。这一步决定了三件事：可以中断、可以刷新恢复、可以「跳到结果」。

const RUN_MS = { win: 56000, none: 56000, fail: 26000 };

function phaseAt(el, scn) {
  const ph = PHASES[scn];
  let cur = ph[0];
  for (const p of ph) if (el >= p.at) cur = p;
  return cur;   // { done:[], run:2, call:"通话中", meta:"已接通" }
}

每个阶段声明「哪些步骤已完成、当前在跑第几步、状态条文案、是否显示声波」，渲染时按这份声明刷 class，不累积状态。

2. 异步与恢复

  • 离开：「等会来看」「有结果了通知我」都只改 notify 并跳到 s6，记录仍是 running，ticker 不停。
  • 刷新：resumeRunning() 遍历记录，把 durationMs - elapsed 作为剩余时间重新挂 setTimeout；已经过期的用 completeIfDue() 立即结算。
  • 结算：finishRun() 只有在 activeRec 存在时生效；如果用户已经离开 s4，结算后只更新记录、弹通知条，不强行跳页。
function finishRun() {
  const rec = activeRec;
  if (!rec) return;
  stopTicker();
  activeRec = null;
  completeRecord(rec);          // status = done, res = buildResult(rec)
  save();
  if (isCurrent("s4")) { renderResult(rec); go("s5", 1); return; }
  renderRecords();
  if (rec.notifyVia && rec.notifyVia !== "inapp") showPush(rec);
}

3. 话术是模板参数化，不是每个品类手写

talkFor(rec) 取 CATS[rec.cat] 的字段，加 rec.price 算出的成交价，拼出三段模板（win / none / fail）。五个步骤对应五组对话，每一步的台词都带品类自己的口径：KTV 问包型和最低消费，酒吧问卡座和开瓶费。

成交那段最后两句是微信留资，只有 win 才有：

{ k: "ai", t: "16:54:33", x: "那我加一下您的" + c.wx.type + "，把确认的信息发过去…" },
{ k: "mer", t: "16:54:46", x: "行，" + c.wx.type + "搜 " + c.wx.id + "，加的时候备注一下。" }

5. 微信留资的呈现

配置在品类上（CATS[cat].wx = {type, id, who, note}），发起询价时快照进 rec.wx，结果页由 wxBlock(rec) 渲染，且只在 scn === "win" 时插入。复制走 navigator.clipboard，失败降级到 execCommand，再失败提示手动添加。

6. 联系人与表单校验

  • 首次询价必须填姓名（1–10 字）和手机号（^1[3-9]\d{9}$），否则「开始询价」按钮禁用。
  • 提交后写入 kanjia.contact.v1，之后只显示脱敏号码（138****1234）和「修改」。
  • 换手机号、换人代订时才需要点「修改」，避免每次重复填。

08扩展指南：加一个品类

整套渲染逻辑不认识「KTV」或「酒吧」，只认识字段。加品类是纯配置工作：

  1. 在 app.js 的 CATS 里加一份配置（约 35 行），必须包含 id / name / store / unit / price / list / ratio / merchant / tel / wx。
  2. 写该品类的 fields（可编辑字段）与 missing（截图里通常没有、需要当场问的项）。
  3. 写三套结果文案：winBenefit / winExtra / rule、noneReason / noneBenefit / noneFree，以及 labels 里的三个字段名。
  4. 如果是休闲品类，把 id 加进 LEISURE 数组，换品类弹层会自动多一项。

不需要动的：首页渲染、字段增删改、询价时间轴、结果卡、记录卡、分享。这些都由 CATS 驱动。

09已知限制与上线前必须补的

这份列表要主动讲，不要等人问。原型最容易被误判成「已经能用」。

现状影响真要上线要做什么
识别是假的：commitScan() 直接把配置里的示例门店写进 state 用户上传自己的截图，识别结果仍是秋果酒店 / 星聚会 KTV，图文对不上 接截图理解（OCR + 结构化抽取），输出必须带置信度与原文位置，低置信字段留空待确认
通话是模板：talkFor() 拼固定台词，没有真实外呼 商家侧的应答、拒绝、临时变价都无法处理 外呼 + ASR/TTS，或人工议价众包；至少要能处理「我要问一下」「这个价做不了」
微信是配置数据：CATS[].wx 预先写死 真实场景必须由商家当场给出，不能预设 从通话中提取 + 二次确认；商家身份要有校验（企业微信主体、门店号）
没有后端：记录只在 localStorage 换设备、清缓存即丢失；无法多端同步 账号体系 + 服务端记录；至少要有任务状态机与幂等重试
没有删除入口 演示数据会一直堆在记录页 左滑删除或长按菜单；删除要同步清理运行中的定时器
分享是占位：三个渠道都只 toast 无法验证分享转化 Web Share API / 生成结果长图 / 带参链接
没有路由：刷新后停在首页 分享链接无法直达某条结果 hash 路由或 /?r=id，配合记录恢复
通知是页面提示条 不真的发短信或服务通知 短信通道 + 模板报备；微信服务号模板消息

合规与信任

  • 代客通话需要告知商家「正在为客人询价」，并按当地要求处理录音与告知。
  • 价格承诺目前是口头的，商家到店不认账没有约束力；可靠的做法是让商家在微信里回一句确认，形成文字记录。
  • 结果卡必须保留「信息仅供参考，需以商家最终确认和实际预订为准」，且不得出现支付成功、订单号。
  • 医美等医疗品类不接：不能承诺疗效、不能打「最低价」，代客议价本身也有争议。
